# Connecting the React Native Frontend to the Rust Backend

This document records the investigation, verification, and fix for the warning:

```
(NOBRIDGE) WARN  [InwardEngine] Native Rust bridge unavailable. Using in-memory JS fallback.
```

## TL;DR — Root Cause

The React Native app was **not running a custom native dev client** that contains the
`InwardCore` TurboModule. The most common cause is launching the app through **Expo Go**
(or a stale dev-client build created before the Rust bridge was wired in). Expo Go never
embeds custom native modules, so `InwardCore` is absent, the provider falls back to the
in-memory JS mock, and the warning is printed.

The Rust backend, the generated UniFFI bindings, and the entire native wiring were all
**correct and working**. The only missing piece was *building and running the custom dev
client* instead of Expo Go.

After building the dev client (`expo run:ios`), the app connected to Rust and the Rust core
created and wrote to its SQLite database (`inward.db`) — proving the bridge is live.

---

## How the bridge is supposed to work

```
React Native (JS)
   └─ src/native/InwardEngineProvider.ts   getInwardEngine()
        ├─ isNativeBridgeAvailable()  → checks TurboModuleRegistry.get('InwardCore')
        ├─ NativeInwardEngine          → requires ./generated (uniffi bindings)
        │     └─ generated/index.tsx   → installRustCrate()  (JSI installer)
        │           └─ C++ JSI  →  libinward_core.a (the Rust static lib)
        └─ MockCoreEngine             → in-memory JS fallback (Expo Go / web)
```

- `InwardCore` is a **C++ JSI TurboModule** generated by `uniffi-bindgen-react-native`.
- On app launch (`app/_layout.tsx` → `getInwardEngine()`), the provider probes for the
  native module. If it is **not** registered, it logs the fallback warning and uses the mock.
- The native module is only present in a build that links the Rust library:
  - iOS: `apps/mobile/build/InwardCore.xcframework` (vendored by `InwardCore.podspec`)
  - Android: `apps/mobile/android/app/src/main/jniLibs/*.so`

## The Fix

You must run a **custom dev client**, not Expo Go. The warning is by-design in Expo Go.

### iOS
```bash
cd apps/mobile
npm run ios          # = expo run:ios  (prebuild + xcodebuild + install + launch)
```
Then, to develop with hot reload, run Metro separately and open the installed
“The Inward Journey” dev-client app (do **not** scan into Expo Go):
```bash
npm run start        # = expo start --dev-client
```

### Android (requires `ANDROID_HOME` / SDK + an emulator or device)
```bash
cd apps/mobile
npm run android      # = expo run:android
```

### Regenerating the native bindings (only needed after Rust API changes)
```bash
# install the ubrn CLI, then:
npm run generate     # builds ios + android native glue from rust/inward_core
```
`ubrn` is optional for *running* the app (the generated artifacts are already committed),
but required if you change the Rust UDL/interface.

## How to confirm the bridge is active (quick check)
1. Launch the **dev-client** build (not Expo Go).
2. Watch Metro / the device log for the engine probe line emitted by
   `src/native/InwardEngineProvider.ts`:
   - `AVAILABLE`  → native Rust bridge is live (good).
   - `UNAVAILABLE` → the running app does **not** contain the `InwardCore` native
     module. The `detail` tells you why (usually
     `require('../native/generated') failed: … TurboModule 'InwardCore' not found…`,
     which means you are in **Expo Go** or a stale build).
3. (iOS simulator) Inspect the app container — a real `inward.db` SQLite file proves Rust
   is persisting data:
   ```bash
   find ~/Library/Developer/CoreSimulator/Devices/<UDID>/data/Containers/Data/Application/*/Documents -name inward.db
   ```

## The #1 cause of "still same issue": loading JS into Expo Go
`expo start --dev-client` prints a QR code. If you scan it with the **Camera app** (or
Expo Go), iOS opens the `exp+inward-journey://…` URL in **Expo Go**, which can NEVER
contain custom native modules → `InwardCore` is absent → the mock fallback fires.

What to do instead:
- After `npm run ios` / `npm run android`, the **dev-client app** ("The Inward Journey")
  is installed on the device/simulator. Open *that* app from the home screen — it
  auto-connects to the running Metro and uses the native bridge.
- If you must scan a QR, make sure it opens in the **dev-client** app, not Expo Go.
- On a physical device you must build the dev client for that device:
  `npx expo run:ios --device` (USB) or `eas build --profile development`.

## Caveats / Notes
- The mock (`MockCoreEngine`) is intended only for Expo Go and web previews; it keeps all
  data in memory and is intentionally non-persistent.
- The Rust static libs were cross-compiled for: `aarch64-apple-ios`, `aarch64-apple-ios-sim`,
  `x86_64-apple-ios`, and the four Android ABIs. The podspec consumes the iOS xcframework;
  the Android build consumes the `.so` files via the `jniLibs` sourceSet.
- `pod install` prints two harmless warnings (`duplicate '-lc++'`, and a simulator
  deployment-target version note for the bundled sqlite). Neither blocks the build.
